PROPERTYPRO — FUTURE PUBLIC DEPLOYMENT PLAN

Purpose
This is a future deployment checklist, not authorization to purchase hosting,
publish the application, or invite users now. Current work focuses on building
and testing the local system. Public deployment begins after the system passes
its required checks and the team explicitly approves a rollout.

1. Release prerequisites
Finish the approved billing workflow and meaningful integration tests.
Verify server-enforced Admin/Manager/Tenant permissions and tenant-record
isolation. Check equal allocation, rent cycles, advance-credit use, duplicate
prevention, correction history, rejection and receipt reuse. Verify supported
OCR documents with independently checked fields. Test failed and retried jobs.
Confirm actual property billing policies match the configured rules.
Finalize supported document boundaries and operational instructions.

2. Hosting selection
Deploy the existing frontend and Laravel backend together, preferably under
one origin. Use maintained Linux hosting with a supported PHP version,
required PHP extensions, Composer, MySQL/MariaDB, private document storage,
HTTPS, scheduled tasks and supervised background workers.
Confirm that the host can run the selected OCR engine and any required PDF
tools, within file-size, memory and processing-time limits. Select a VPS or
managed environment based on these proven requirements and team budget.
Do not assume a free hosting tier supports OCR or long-running workers.
React, Vue, microservices and a different database are not required for rollout.

3. Domain and HTTPS
Choose a domain or provider subdomain, configure DNS, and enable renewable
HTTPS certificates. Check certificate renewal and HTTPS redirects.
Test browser push and service-worker registration on the deployed origin.
Local browser subscriptions do not automatically become public-site
subscriptions; tenants must grant permission/register on the public origin.
Push remains optional and authenticated portal access must work without it.

4. Production configuration
Expose only Laravel's public directory. Set production environment values,
disable debug output, and keep secrets outside version control and public files.
Configure the production application URL, sessions, CSRF protection, secure
cookies, allowed origins and trusted proxies as appropriate to the host.
Use a restricted database account and separate production credentials.
Create and protect the application encryption key; preserve it across releases.
Configure the designated mailbox for utility intake only and protect its
credentials. Configure Web Push keys separately and preserve them securely.
Never expose database management panels or the local XAMPP setup publicly.

5. Database and files
Back up the database before migrations. Apply reviewed migrations using a
documented release procedure. Do not copy demo identities, fake bills or
default passwords into real-user accounts.
Store utility-bill sources and receipts privately; serve them only after
authentication and record-level authorization. Protect backup storage too.
Keep source records, allocations, corrections, confirmed payments and receipts
linked. Preserve original transaction history and finalized membership snapshots.
Record all timestamps consistently and apply Philippine-time billing/reminder
rules explicitly.

6. Scheduled work and queues
Run the Laravel scheduler and a supervised queue worker. Configure email
polling, OCR, rent generation and notification jobs according to implemented
requirements. Set practical timeouts and retries based on measured workloads.
Use idempotency and database constraints to prevent repeated charges,
allocations, credit applications, receipts or reminders.
Track failed jobs and provide a documented recovery procedure. Restart workers
as part of releases so they load updated code.

7. Backups and monitoring
Define backup frequency and retention with the team and property operator.
Schedule database and private-file backups and test restoration before launch.
Monitor application errors, failed jobs, scheduler operation, storage capacity
and observable push-service acceptance/failure. Do not treat push acceptance as
delivery or readership. Avoid logging passwords, secrets or unnecessary tenant
details. Establish who receives operational failures and maintains the server.

8. Pilot and acceptance
Use a separate staging environment or clearly isolated test dataset first.
Run tests with Admin, Manager and multiple Tenant accounts, including shared
occupancy. Verify actual mailbox intake, supported OCR samples, billing,
Manager confirmation, receipt access and optional push on supported browsers.
Test account/device changes, expired subscriptions, denied permission and
portal fallback. Complete a small authorized pilot before broader invitations.
Resolve material failures before rollout; do not invent successful results.

9. Release and rollback
Prepare a versioned release, migration notes, smoke checks and database/file
backup. Obtain explicit approval before public publication or user invitations.
After rollout, verify login, permissions, billing access, workers and scheduler.
Define rollback steps before deployment. Database schema rollback must account
for new transactions; restoring an old backup can lose post-release records.
Use maintenance windows where changes could interrupt billing or payments.

10. Operating cost and responsibility
Open-source software does not eliminate hosting, domain, storage, backup or
maintenance costs. Confirm current provider prices and limits before purchase.
Assign responsibility for updates, credentials, backups, failed-job recovery
and user support. Prepare appropriate handling of real tenant information;
the capstone security evaluation is not legal certification.

Scope lock
Public hosting does not expand the approved system scope. Keep rent,
electricity and water only; predefined rules; Manager verification; equal
shared allocation; supported OCR layouts; and Web Push as the external tenant
notification channel. Do not add payment gateways, SMS/email tenant alerts,
autonomous AI decisions or other excluded functions through deployment.
